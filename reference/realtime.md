# Realtime & Multiplayer Orgs — Authoring Transition Rules

**The on-demand reference for org config authors building a realtime or
multiplayer org.** Scoped to the transition engine's paths, so an
`orgs/**/config.json` session does NOT auto-load it — `org-config.md` carries a
headline index pointing here. Read it in full when writing `app.transitions`.

## Authoring a `transitionRule` (`app.transitions` — human/Claude only, `promptHidden`)

`transitionRule` stays `promptHidden` so the org-gen agent never authors it, but since #1320 it IS in the admin designer — the `app` node's **Transitions** tab (a `transitionRules` MasterDetail in `editorOverrides.ts`, sibling of `pushNotifications`). The traps below apply to both entry paths. Rules read the transition-scope vars `$record`/`$recordId`/`$target`/`$records`/`$params`/`$now`/`$seed`/`$private` (`TRANSITION_SCOPE_VARS` — never shared's UI `KNOWN_SPECIAL_VARS`).

- **Test a rule from the org pack with `createTransitionSim(loadOrgTree(…), { username, orgName, records })` (`packages/shared/src/orgicore/utils/test/transitionSim.ts`): the REAL engine, arming and firing cores over the shared fake, the mirror built as publish builds it, every engine write re-fired.** `write` returns each event's results (`describeEvents`); `race(a, b)` runs b inside a's transaction window for a real `stale`; a chain past `maxRefires` throws `TransitionLoopError`. The default clock ticks per event on purpose: a constant `$now` repeats the ack byte for byte, the fake fires nothing, and an ack loop passes. Not covered: botActor, push/SMS. References: squiggly's `rotate.test.ts` (onWrite) and `timers.test.ts`; for whole games played by the shipped bot brain over several `seed`s, cassino's `wholeHand.test.ts` and shuffly's `wholeRound.test.ts` (#2527). (#1826, #2504)
- **Timers in the sim (#2504): creation runs the publish reconcile (`await sim.ready`), every write arms, and `advanceTime(ms)` fires what falls due, soonest first, with `$now` = the dispatch time; `pendingTimers()`, `armedMarker()`, `archived()`/`failArchive()` to assert; past `maxFires` it throws `TimerLoopError`.** Every write ticks the clock, so a deadline from `sim.clock()` taken BEFORE a write lands a tick or two early; advance to an absolute time (`advanceTime(t - sim.clock())`). A superseded deadline's task still dispatches at ITS time, as a `stale-drop`. A firing that throws is reported and dropped; Cloud Tasks retries are not simulated.
- **A rule's formula scope includes the org's `function` nodes (#1546), stamped PER RULE on the mirror — only the transitive closure over that rule's formula fields (~200 B for squiggly vs 7.6 KB for all its nodes).** Every consumer already reads a rule (`timerFire` reads ONE at `byTimerType/{type}/{ruleKey}`), so bodies inside it cost no extra read; binding is the `OrgFunction` marker and shared's evaluator does the rest. A body may NOT read `$now`/`$target` — pass transition state as a PARAMETER (`function-transition-scope-var`, `shared-generation.md`) — and the gate rejects an unresolvable call at publish, which is what makes the arming and firing paths resolve the same functions. (#1546)
- **`functions` and `consts` are REQUIRED on `SharedRuleContextInput` because NINE sites build a rule context (grep `RuleContext(`)** — engine's pre-check, `privateReadUids` keys, in-transaction and notify contexts, arming's `dueAt`, timerFire's re-derivation, the mirror's perpetual `seed` (#1521), `botActor`, and the Bluffy playtest harness (`packages/cli/src/playtest/bluffy/reads.ts`) — and a field omitted at one fails silently on that path only. This bullet said FOUR until #2317 counted; trust tsc, not the number: #1369 made `private` required and tsc named `arming.ts` and `timerFire.ts` at once.
- **An ABSENT `trigger` is safe and means `onWrite`** — the write engine fires on `watchType` + `enabled` and never reads `trigger`, and the closing gate treats unset (or `""`, what the designer serialises) as `onWrite`. (#1320, #1534)
- **`next` returns the ENTIRE target record, not a patch** — the engine writes what `next` returns (then prunes `undefined`). Spread and override: `@{ ...$target, round: $target.round + 1 }`.
- **`length(arr)`, not `arr.length`.** The formula engine has no array `.length` — static property access MAPS over elements (`arr.length` → `[undefined, …]`, re-probed for #1521).
- **Parenthesize the final ternary in a `;`-script** — jsep's `;`-statement gobble otherwise mis-parses a bare trailing ternary.
- **Anything a rule writes to RTDB and re-reads across steps must be tested through the array-coercion.** RTDB returns an integer-keyed map as a SPARSE array whenever `maxKey < 2 * numKeys` (the SDK's `ChildrenNode.val()`): `{1:e1,2:e2}` → `[ ,e1,e2]` with a HOLE, not a `null`, at 0, and a lone `{1: x}` → `[ , x]`. This bullet said `[null,…]` and "a lone `{1: x}` stays a map" until #2504's emulator contract run disproved both. `createTransitionSim` (above) reads every value back through `rtdbCoerce`, as does `cloud-functions/test/evalRule.test.ts`'s older replay — the pure in-memory pipeline does not. (#1258, #1826, #2504)
- **A transition rule has NO repo access — `sharedScope` is exactly `$target/$records/$params/$now/$seed` (+ `$private`, + org functions), with no `$data` or `byId` — and `$records` is the WATCHED type's collection only.** So any logic a rule runs must be PURE or derivable from the record's own id: shuffly's meld chain bottomed out in `byId("Card", id)` and couldn't run server-side until ids became self-describing (`card_1s7` → `parseCardIdFn`), with a test pinning the generated set to the embedded instances. Cross-type data (seat → auth uid) is computed where `$data` exists — the client starting the game writes `seatUids` onto the target — and handed to the engine as state, not looked up. Check BEFORE designing a rule that "re-validates authoritatively". (#1369)
- **`privateReadUids` → `$private` is the READ half of the private rail, and it is a PRE-TRANSACTION snapshot that does not re-resolve on a retry.** The updater is synchronous by contract and cannot await, so the read happens once in `runRule`. Anything needing serialisation must be guarded by a `condition` on the PUBLIC target, whose compare-and-set is what actually orders concurrent moves — `$private` alone orders nothing. (#1369)
- **`privateReadUids` is evaluated on EVERY write of the watched type, BEFORE the condition — so gate the KEY formula on the public record, not just the condition.** `runRule` resolves the target, then the key list, then `$private`, and only then evaluates `condition`: a rule that reads five piles to decide it doesn't apply has already paid for five reads on every move in the game. The fix is one ternary in the key formula itself (`@$record.kind == 'deal' && $target.phase == 'playing' ? dealKeysFn($target) : []`) — `[]` is explicitly accepted and reads nothing, while `null` is a formula error. Cheap public state gates the expensive private read. (#1906)
- **`next` and `nextPrivate` are evaluated against the SAME pre-write `$target`, inside one transaction pass** (`commitGuarded` builds the context once from `cur`) — so a helper handed the already-updated public value computes from state that was never committed. Shuffly's draw takes the top of the discard pile: fed the post-draw `Game`, it took the NEW top, a card still in the pile, and DUPLICATED it. Only a conservation assertion over a multi-step sequence catches that class; a single-step test agrees with the bug. (#1371)
- **`nextPrivate` REPLACES a private record wholesale, it never patches it — so a rule mutating one must make its `condition` prove it actually READ it.** Shuffly's `drawOkFn` requires the mover's hand to be non-empty: `$private` omits a key with no record, so a failed or mis-keyed private read yields `[]`, and without the guard the draw still "succeeds", writing a one-card pile over thirteen. The condition is the only thing between a stale client and unrecoverable data loss. (#1371)
- **Every formula field on `transitionRule` must be in `rulesMirror.ts`'s ONE list, `ruleFormulaFields` (feeding `referencesRecords`, `reachableFunctions`, `reachableConsts`), and in the gate's `TRANSITION_FORMULA_FIELDS` (`validation/formulas.ts`).** Missed by the mirror, a function or const used only in that field resolves to `undefined` AT RUNTIME (the gate says it resolves) and `$records` reads `[]`. #2317 merged the mirror's per-analysis copies; the guard is DERIVED: `rulesMirror.test.ts` reads `nodeModel.json` (`@-formula` in a field's own description is the marker), pins the exact set and probes each field through all three — add a field to the model and it goes red, as it did for `seed` (#1521). (#1369, #1371, #2317)
- **`notifyTurnUidField` must name a field carrying the FIREBASE AUTH uid (a `generateId()` `playerId` matches no device, silently — plumb `ownerUid` through `next`), and it stays onWrite-only and one-uid: the gate rejects it on a timer rule.** A reminder or roster push is `notifyTo` (#2325): four formulas (`notifyTo`/`notifyTitle`/`notifyBody`/`notifyKey`) evaluated AFTER an `applied` commit against the COMMITTED `$target` and the commit's `$now`, on either trigger; recipients are auth uids or `{uid, title?, body?}`. **Reminder idiom:** `next` stamps `remindedAt: $now` on everyone due (that moves `dueAt` on) and `notifyTo` sends to `filter(…, it.remindedAt == $now)`. At most once per commit, so `notifyKey` is only for a rule that can apply twice for the same news. On iOS the subscribed uid is the installed app's, not the Safari tab's. (#1365, #2256, rallyround #2271)
- **`pushNotifyTurn`'s dedupe marker (`pushSent/turn/{type}/{recordId}`) records a turn that was DELIVERED, not attempted — written only after a send reaches ≥1 device.** Advancing it first makes any non-delivery (rate limit, transient FCM failure) permanently skip that turn. The deliberate trade is a possible double-send on a race. Only `byTargetType[type][0]` fires — a second turn-notifying rule on the same target type is silently ignored, with no gate warning. (#1365)
- **A text is `smsTo` (#2254), the second channel of the same post-commit side effect, and it is the ONE place a timer rule can reach the private rail.** `smsReadUids` + `smsPrivateType` load records AFTER the commit, outside the transaction, so a reminder timer can read the organiser's phone book and an onWrite confirmation sees the number its own `nextPrivate` just stored. `$private` is bound in `smsTo`/`smsBody` only, and stays rejected in `notify*`. Never put a sender in config: the sender ID is platform state (`og sms-sender`, default `Orgiggly`), so name the event in `smsBody`. A commit over the hourly/monthly segment cap texts NOBODY (all or nothing), but the commit still applies.
- **Parent/child CASCADE delete (#1972) is checked in the wildcard trigger BEFORE the `byWatchType` mirror read, and that ordering is the whole feature.** A child objectType declares `parent: { type, idField }`; publish inverts every declaration into a fourth mirror index, `transitionRules/childrenOf`; on a DELETE the engine reads it and reaps matching children. It runs ahead of step 1 because a parent type is normally a rule TARGET, never a watched one — `Game` would exit at `no-rules` and its children outlive it. Multi-level cascade is free (each child delete re-fires the trigger) and terminates only because the closing gate rejects a cycle (`parent-relation-cycle`) — load-bearing, not hygiene. Admin-SDK deletes fire triggers too. `buildMirror` removes a node only when `childrenOf` AND `byWatchType` are empty; `byWatchType` alone disables a CASCADE-only org (#1537's shape).
- **The cascade reaps the PRIVATE rail too, with no declaration: publish derives `privateOf` (target type → every `privateType` its rules write) and a delete of `{Type}/{id}` removes `realtimePrivate/{key}/{privateType}/{id}` under every key.** A private type cannot take `parent:` (it has no id field: it shares its target's id), so before this a retired Game left every hand, bot pile and deck behind. It reads the whole `realtimePrivate` node per delete (no shallow read in the admin SDK). A game org should still declare `parent: { type: "Game", idField: "gameId" }` on its Move/Flag/Player types — bluffy and handsofvictory shipped without it, and their EOL rule deleted only the Game.
- **To KEEP a finished record browsable after its end of life, add `archive: true` to the `endOfLife` rule (#1191).** `timerFire` copies it to Storage just before the delete; a failed copy blocks the delete and retries. Read it back with a subsection declaring `source: "storage"` and NO `scope` — `$data.Type` merges both rails. An archive publish fires any push rule on that type. **Shape the copy with `archiveData` (a projection: Storage is world-readable, so keep phones and uids out), `archiveType` (`EventArchive` beside a live `Event`) and `archiveId` (`@$target.id + '-' + $target.date` for a reused id).** The id must be pure so a retry overwrites its own copy (the gate rejects `$now`/`$seed`/`generateId()`); a bad value archives nothing. Deploy `timerFire` BEFORE publishing any of this: an old one deletes without archiving, or copies the WHOLE record. (#1191, #2324)
- **Pack-test a timer rule end to end in `createTransitionSim` (arm, `advanceTime`, fire, cascade); a lone `dueAt` formula is quicker with `createOrgPackApi(tree, { context: { $target: rec } })` then `evalAt(rule.dueAt)`.** Before writing a reaper, check a `parent:` cascade doesn't already do it. Changing a shipped org's rules or functions breaks suites OUTSIDE `test:orgs` that read its config as authored (`reaperRules.test.ts`, `evalRule.test.ts`'s squiggly oracle, the org's E2E spec, which finds rules by label) — #1191 was green on `test:orgs` and red on all three. Timers DO fire under the emulator; to make a record due in an E2E, clear its `armed/` marker before writing a past deadline, since a RE-arm to the past waits 60 s (`lab/scheduleTest`); the emulator enforces that floor only since #2413, which is how rallyround and squiggly's stall-breaker forgot the clear. (#1810, #1190, #1191, #1521)
- **A `dueAt` from a date the organiser typed: `dateFrom(d).toZonedDateTime({ timeZone: 'Europe/London' }).add({ minutes: m }).epochMilliseconds`** gives UK wall-clock epoch ms, BST included. Temporal methods dispatch member-style, and the validator's native-method allowlist knows the conversions since #2264. There is no browser-timezone variable, so name the zone. `dateFrom` returns an `<<INVALID_DATE…>>` string (no `.year`) for a bad date, so guard on `dateFrom(d).year != null`. Work it out in the client at save time and store it on the record, as rallyround's `dayStartAt` does. (dave/rallyround #2264)
- **A recurring wall-clock job ("every day at 05:17 London") is a `perpetual` `onTimer` rule on its OWN schedule type — no cron trigger, no bespoke CF (#1521).** `{ trigger: "onTimer", targetType: "DailyReset", perpetual: true, targetId: "daily", seed: "@{ nextAt: nextOccurrence($now, '05:17', 'Europe/London') }", dueAt: "@$target.nextAt", condition: "@$now >= $target.nextAt", next: "@{ ...$target, nextAt: nextOccurrence($now, '05:17', 'Europe/London') }" }`. Publishing creates the record from `seed` (never overwriting a running one), so no script writes it. The gate holds a perpetual type to ONE rule and no other timers (arming would cross-wire them), wants `dueAt` as a plain field read, and exempts the type from end-of-life. A firing writes ONE realtime record: Storage publishes, AI calls and email still need a bespoke CF like `closeDailySpot`. Worked org: `lab/scheduleTest`.

## Authoring a `botActor` (`app.botActors` — server-side bot seats, #2135 / epic #2132)

A `botActor` is a helperType beside `transitionRule` (same `promptHidden` + `ui.omit` posture: hand/Claude-authored, no designer tab yet). The `botActor` CF is a second wildcard `onValueWritten` over every realtime write: one shallow read of `transitionRules/botActors/{type}` (null ⇒ exit), then per actor `isBotTurn` → `$seat` → `privateKey` read (re-read until `privateReady`) → `$private` → `state` → `$state` → `moveId` → exists? stop → `delayMs` beat ∥ decider → `$decision` → `move` (or `fallbackMove`) → create-if-absent write of ONE `moveType` record with `ownerUid` = the private key. The engine then validates that move like a human's tap.

- **`watchType` ≠ `moveType` is the loop gate, and `moveType` is STATIC so the gate is a publish-time error (`botactor-self-target`), not a runtime discovery.** The bot's own move write IS a watched-type write for the engine (desired — the rules validate it) and an unwatched-type write for the bot (null mirror read). The mirror drops a self-targeting actor as a defensive floor.
- **The private piles land one round-trip AFTER the public record, and the actor fires on the public write — so a bot can read the PREVIOUS deal's cards.** Bluffy's Tex opened hand 45 on hand 44's A♥4♥, 51 ms after the deal (2 of ~650 decisions). Stamp the pile with a generation the public record also carries and declare `privateReady` (`@$private[key].gen == $record.dealGen`): the actor re-reads on a 100 ms beat and, after 2 s, writes nothing (`private-stale`) rather than play the wrong hand. Any actor with a `privateKey` needs one. (#2296)
- **Idempotency is `moveId` → read-then-transaction.** Re-delivery exits at the existence pre-read before the think-beat and the decider call; a concurrent second delivery aborts in the transaction. Make `moveId` a pure function of the decision point (`recordId + handNo + street + seat`) — never `$now`/`$seed`. **Several Moves in one turn (a power, then the bet) need a key that changes after each**, or the next wake is a duplicate and the seat stalls (HoV: `curBet` + `length(powerFeed)`). (#2217)
- **Scope grows field by field: `$record`/`$recordId` (+ `$target` alias), `$params`, `$now`, `$seed`, then `$seat`, `$private`, `$state`, then `$decision` in `move` only.** `fallbackMove` runs precisely when there was no decision, so it must not read `$decision`. **`$seat` is a STRING**: `"3" + 1` is `"31"` — recompute a numeric seat from `$record` (HoV `botSeatFn`). (#2217) The formulas stage gates these by path (`appConfig.botActors[i].<field>`, `BOT_ACTOR_SCOPE_VARS`).
- **Compute numbers in `state`; let the decider judge.** Jev is literal and bad at arithmetic (its published jaggedness list) — pot odds, stack ratios and `handRank(...)` category belong in the formula, and only the judgement in the question. Pin what `questions` returns to the Jev shapes (`choice` criteria = option→description object; `score` criteria = ordered array; `noul` = none) — an unshaped map falls back rather than asking, while an EMPTY map is "nothing to ask" (applied, `$decision = {}`, no call, no stats sample; #2230). Keys the `move` formula prefixes with `_` are journal-only: kept in the decision journal, stripped from the public record (the rail is public: `baseline: fold` on a raise would announce a bluff).
- **Every formula field on `botActor` is listed in THREE places that must agree: the mirror's `BOT_ACTOR_FORMULA_FIELDS` (closure stamping), `validation/formulas.ts`'s set (scope gate) and `validation/botActors.ts`'s (unknown-call gate).** A field missing from the mirror list makes an org function called only from it resolve to `undefined` at runtime.
- **The mirror lives UNDER `transitionRules` (`transitionRules/botActors/{watchType}`) to inherit its admin-only RTDB lock** — no `database.rules.json` change, no rules deploy. Any new top-level mirror key still has to be added to `runRulesMirror`'s named-key `update()` literal AND the `Mirror` type.
- **A phase a TIMER can close, or that bots must act in simultaneously, resolves in a Dealer botActor's onWrite rule.** A timer can't read the rail and the botActor writes ONE move per Game write for ONE seat — so HoV's pineapple Seal applies the bots' discards itself, and a fold-out (the shot clock can fold the last opponent) stops at `turnPhase: "foldOut"` for a Dealer Settle that reads every pile. An existing public rule can gain a conditional private side: a gated `privateReadUids`, condition `!due || readOk`, and `nextPrivate: due ? piles : {}` — `{}` writes nothing. (#2211, #2216)

## Authoring the org config side

- **An `onTimer` rule cannot read (`privateReadUids` is rejected: `transition-private-read-timer`) or write (`commitGuarded` never evaluates `nextPrivate` on the timer path) the private rail — so deal every per-player secret at Start and have the timer write only PUBLIC state for the next `onWrite` rule to fold in.** `dave/bandwagon` deals briefs to every seat inside `Start the session`'s `nextPrivate`; its timer (`Fill a stalled line`, onTimer) appends a filler line to a public `pendingFillers` array and can flip `phase` to `closing`, and `Write a line` (onWrite) reads $private + pendingFillers together to build the final lyric list.
- **A live multiplayer room must be ONE phase-gated screen, not a screen per phase — `screen` has no auto-navigate field, so nothing can pull a player off a stale view.** `nodeModel.json` gives a screen no way to react to a formula going true, so the only lever a separate results/lobby screen has is a button, and whoever does not press it is stranded: `dave/jumbly` shipped a `reveal` screen and a guest sat on it through the next round. `dave/shuffly` and `dave/cassino` gate every phase on `lobby` and nobody ever navigates. Folding jumbly's back cost -3.5 KB of config, because the extra screen had re-declared probes and variables the room already had. (#1931)
- **On a phase-gated single screen, no action may `navigate` to the screen it lives on — `navigate` is `pushCursor`, whose contract is "nav-stack entry + flow-state RESET under the target".** Self-navigating therefore clears the subtree the screen's own realtime probe subsections live in, and the screen stops updating for whoever pressed it until something genuinely remounts (leaving and returning fixes it, which is what makes it look like a sync bug). `dave/jumbly` folded its reveal into `lobby` and left one `navigate("lobby")` behind on the Next-round button: the host pressed it, the guest's board arrived and his did not. Folding screens together makes every surviving `navigate` a suspect, so assert the class over the whole config, not the node you just moved. (#1949)
- **`setRealtime` is a FULL REPLACE, so a field merely OMITTED from the object literal is DELETED — change some fields of an existing record with `updateRealtime` (shallow merge, #1827).** Silently: squiggly's `stepStartGame` dropped `enableVideo`, every `videoRoom` hid with its Leave button, and a closed tab billed 552 credits. `updateRealtime` keeps unmentioned fields, `null` deletes one, a nested object replaces that field, and it never restamps `createdAt` — so CREATE with `setRealtime`, or a `createdAt`-keyed reaper can't arm. **Classify each site by SHAPE (#2322):** a spread or a literal re-carrying existing fields is a CHANGE → `updateRealtime`; keep `setRealtime` for creates, deliberate resets and full upserts. Pin with `createRealtimeStore` (`orgPack.ts`) asserting the record PLUS the write `kind` — a spread replace leaves the same values.
- **Input that must never be public (a phone number): declare the type `scope: "inbox"` (#2253).** The realtime hosts route it to `realtimeInbox/{uid}/{Type}/{id}` with no script change: writer-only read/write, org admins read, named orgs only. `realtimeInboxTransition` runs the same rules — ack on the inbox record, `$records` = that writer's only, `$record.ownerUid` = path uid; a rule may watch an inbox type, never target it. Engine tests must write there and pass `inboxUid`. (dave/rallyround #2269)
- **Give each device ONE input record at a fixed key (`setRealtime("Claim/" + $authUid, …)`, overwritten by every action, plus `removeRealtimeOnDisconnect`) when its input carries something that must not linger in public realtime** — or better, make it an inbox type (above), which keeps this idiom and never touches public realtime at all. The obvious "remove it once the result is known" can't be written: no script runs on a reactive change, async host calls are top-level only (`evalScriptAsync`), deleting a missing record is refused for non-admins, and no rule can delete a watched type. Add a `nonce` (`generateId(10)`): RTDB fires nothing for a write that changes nothing, so a repeat tap would never reach the engine. The rule then can't use `$recordId` as a per-action id; derive one (`$recordId + '-' + $now`). (dave/rallyround #2265)
- **Realtime "room handoff": to migrate live players to a new realtime record, stamp a POINTER field on the OLD (host-owned) record rather than resetting the reused one.** Reusing a key re-collides child records keyed by it (Squiggly's submissions key on `gameId+round`, so every game restarts at the same round); a fresh key is a fresh keyspace. Non-hosts already subscribe to the old record, so a `nextRoomCode` pointer reaches them reactively → a `rel` "Join" anchor whose `flowStep:script` re-keys their presence. Zero CF change. (#1204)
- **Engine-only private state goes under a RESERVED NON-UID KEY on an existing `scope: "user"` type — not a second type.** `privateType` is one string per transition rule, so a rule needing both per-player records AND a shared hidden pile in one atomic write puts them on the same type and keys the pile `__stock` (any segment no Firebase auth uid can equal; `buildPrivateUpdates` bars `. # $ / [ ]` **and empty**). The `realtimePrivate/$uid` grant is `auth.uid === $uid`, so that subtree is readable by nobody while the admin-SDK engine still writes it. This deliberately INVERTS nodeModel's `nextPrivate` warning, where a non-uid key is a silent bug — comment it at the declaration, and note the residual assumption: it is safe only because uids are not client-chosen. (#1369, shuffly's hidden stock)
- **That empty-key rejection kills the WHOLE fan-out, so every seat in a `nextPrivate` reduce needs a key that exists — bot seats included.** A seat→uid map is partial: cassino's `playerUidOf` returns `""` for a bot deliberately (#1901), which failed every deal at a table with one. **Discriminate on an explicit public list (`Game.botSeats`), NOT on the empty uid** — a signed-out human maps to `""` too, and giving them a substitute key deals a real hand where they can't read it, silently; a refused write is the loud failure you want. **Which key you substitute decides who can READ the hand:** a reserved `__bot{n}` is unreadable by every client — right for a server-side bot, fatal for a host-driven one (#1910 re-keyed cassino's bots into their host's record). (#1906, #1910)
- **A phase field on the TARGET record is the cheapest idempotency guard a transition rule can have, and it doubles as the UI's affordance state.** Shuffly's `Game.turnPhase` (`draw`|`discard`) means a re-delivered draw finds `discard` and resolves `condition-false` at the pre-transaction check, before any transaction — no per-move dedupe table, and the same field drives whether the Discard button is enabled. Read an ABSENT value as the safe default (`turnPhaseOfFn` → `"draw"`) so records written before the field existed stay usable instead of stuck. (#1371)
- **Denormalise the DISPLAY value, keep the authority somewhere else, and re-derive rather than increment.** `Game.discard` is the pile and `upcard` is just its top, re-derived by the rule on every change; `stockCount` is recomputed from the hidden pile's length, never decremented — so a counter that ever drifted heals on the next move instead of compounding. A rule that increments is a rule that can only get further from the truth. (#1371)
- **A client formula can read the engine's reserved `_moveOutcome` ack subkey even though it is undeclared on the objectType** — a realtime snapshot is spread wholesale into the repo object (`storageObjToRepoObj`), so the field arrives intact. Find the player's own latest input record with `sort(filter($data.Move, …), "createdAt", true)[0]`: every realtime write carries `createdAt` (`buildRealtimeWriteRecord`), so ordering needs no field of your own. (#1371)
- **A rejected move's `rejectionReason` is evaluated against the `$target` its OWN transaction saw — in a genuine race that is the PRE-commit state, so a fallthrough of "every guard passed ⇒ some other cause" lies.** Shuffly's deny-vs-claim loser was told "You are not seated at this table." A rule that can lose a race needs a race-honest last branch ("Too late — someone got there just before you"). **Since #2333 the in-transaction loser (`stale`) is acked too, against the LIVE target** — the winner's committed state. Test both paths: `Promise.all` of two `runTransition`s usually yields `condition-false`, so force `stale` with the fake's `hooks.beforeTxCurrent` (rallyround's race test passed for months on a lucky interleaving). (#1378, #2260, #2333)
- **Reset a realtime record between phases by OMISSION: the client `setRealtime` host is a `set` (replace) and a rule's `next` replaces the record inside its transaction.** Build it from an explicit carry-over list; never `{ ...game, x: null }`. Never pass `undefined` either (RTDB rejects the write), and an empty UNDECLARED object/array round-trips as ABSENT — declare collection fields (`list<T>`/`map<T>`, #1860) so hydration restores `[]`/`{}`, or guard undeclared ones (`deal: (old.deal ? old.deal : {})`). **The carry-over list is where a later feature silently dies, so audit by SHAPE, not by grepping `setRealtime`:** shuffly's `enableVideo` needed carrying at four sites and the missed one was `nextRoundGameFn`, a plain function returning a literal (#1886). Pin each producer's literal with an org pack case, then delete a carry and watch it go red. (#1204, #1380, #1886)
- **Config-driven values a RULE needs must be `const` nodes (or functions); `buildMirror` stamps per rule the closure of the functions it CALLS and the consts it, or those bodies, READ.** A rule sees no repo, so a `ScoreCategory`-style type is unreachable from the rule that scores with it (cassino's `scoreWeights` is a const). Since #2317 the gate rejects any other bare name in rule/actor scope (`transition-unknown-identifier`, `botactor-unknown-identifier`) — a `variable` read once published clean and evaluated `undefined` — yet it skips every `$`-name and allows a `byId` call, so a pack test still walks `appConfig.transitions` and checks nothing reachable touches `$data`/`byId`. **A malformed `condition` fails silently too**: jumbly's C-style comma expression (no such operator, only `let a = x; rest`) meant the rule NEVER FIRED while every pack test stayed green. Only a test driving the real engine catches it — an org-pack `createTransitionSim` test for onWrite rules (#1826), a `cloud-functions/test/*Rules.test.ts` for timers; write one per org with rules. (#1902, #1927, #1909, #2317)
- **Such a harness must pass `extractConstNodes(CONFIG)` to `buildMirror`, as publish does — an unbound const HANGS it rather than failing.** HoV's and Bluffy's passed functions only; cardroom v2's `rankCodes` came out unbound, the deck empty, and a play-it-out `while` spun at 100% CPU. Both now refuse to load short of a 52-card deck. (#2361)
- **A value a rule reads is a `const` node, not a `variable` with a literal `compute` (#2317's design (a), not (b)): a variable's `compute` is only a DEFAULT that stored data overrides on the web (`createSelectValue.ts`), so a server-stamped copy diverges on the first write; a const is never evaluated or overridden.** Consts reach transition rules and bot actors ONLY — a `pushNotifications` `condition` evaluates against the record alone and sees no const or function; the gate rejects either there (`notification-unknown-identifier`/`-call`, #2353). The mirror stamps each const — like any arbitrary JSON — as a JSON STRING (`MirrorRule.consts`): RTDB rejects keys holding `.`/`$`/`#`/`[`/`]`/`/`, drops an empty `{}`/`[]` and reads an integer-keyed map back as an array; `sharedScope` parses it once per context.
- **Rules sharing one Move kind run in SEQUENCE against COMMITTED state, so a later rule sees an earlier one's write.** Cassino's four deal-family rules all fire on `kind: "deal"`, told apart only by their conditions. `End the hand` (condition: phase `playing`) wrote phase `handOver`, which immediately satisfied `Start the next hand` (condition: phase `handOver`) — so one tap scored a hand, dealt the next, played it, scored it again: `totals` 27 against `scores` of 10. A rule whose condition consumes another rule's OUTPUT phase needs its own Move kind. Every org-pack test stayed green; only a real `runTransition` walk shows it. (#1909)
- **`null`, `undefined` and `""` must ALL read as "absent" for an optional id a rule receives** — RTDB drops a null key, and a param crossing the widget bridge can arrive as an empty string. Cassino's `buildOkCoreFn` tested only `move.buildOnto == null` while its state twin also allowed `""`, so every fresh build committed from the widget was refused as `noSuchBuild`. Both the org pack and the widget suite stayed green, because each passes `null` — only the move driven through the real engine failed. Normalise through ONE predicate shared by validator and state function, and pin it with `it.each([null, undefined, ""])`. (#1908)
