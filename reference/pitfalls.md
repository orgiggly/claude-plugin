# Node pitfalls

Traps per node type: things a config can say that validate but don't behave the way they read.

## App node pitfalls

- The app's `appLogo` field is admin-managed (uploaded via the design-tab widget). Do not generate it — it'll be stripped on publish.
- `authMode` accepts only `"public"` or `"private"`. Legacy values (`anonOnly`, `hybrid`, `userOnly`) are mapped at load time but should not be generated.
- `theme` and `themeColors` configure site chrome. The `palette.mode` you pick (`"light"` or `"dark"`) flips MUI dark variants for portal-rendered components — pair it with `themeColors` overrides if you want a non-default look.
- Shared CSS goes in the app node's `customCss` — one copy, injected on every screen. Never paste the same `<style>` block into each screen's content node: a screen-scoped `<style>` unmounts on navigation, which is exactly why `customCss` exists. Keep genuinely screen-specific rules in that screen's own `<style>`; they win on document order.
- Set `contentMaxWidth` (px) on the app node for a form or content org, e.g. `"contentMaxWidth": 720`. Every screen's content then sits in one centred column on a wide window, so built-in inputs and widgets line up with the HTML instead of stretching edge to edge. Your HTML then needs no `max-width` / `margin: 0 auto` of its own. Leave it unset for a dashboard, calendar or multi-column grid that wants the full window, or give that one screen `"containerStyle": { "maxWidth": 0 }` to opt it out.

## Tree node pitfalls

- A data-bound `tree` renders stored RECORDS, not authored child nodes: `nodeTypes` keys are **ObjectType names** and the hierarchy is linked by each child record's parent link (below), never by `_children`. `rootType` must itself be one of the `nodeTypes` keys.
- Always set the data block explicitly — `"data": { "source": "storage", "scope": "global" }`. With no `data.source` the tree is UNBOUND: it renders "This tree isn't connected to a data source yet" and the record-mode checks below are skipped rather than reported, so the mistake is silent. `"source": "embedded"` renders the seeded `objectInstances` and IS writable: add/edit lands in a per-browser local overlay, so rows reappear and survive reload on that device but are never shared with anyone else. Use `storage` + `scope` when records must be visible across devices or users. (An earlier version of this bullet said embedded writes "never appear" — that was WRONG since the local rail landed.)
- `nodeTypes` keys are ObjectType names and each value is a `TreeNodeOptions` (shape above) — e.g. `"nodeTypes": { "Project": { "allowedChildTypes": ["Epic", "Task"], "icon": "folder" }, "Epic": { "allowedChildTypes": ["Task"] }, "Task": { "allowedChildTypes": [], "labelField": "title" } }`. A leaf type declares `allowedChildTypes: []`.
- Child records link to their parent through the platform-written `_parent: { "id": …, "type": … }` member — declare NOTHING for it. A child ObjectType is just its own fields, e.g. `{ "type": "objectType", "name": "Task", "fields": [{ "name": "title", "type": "text" }] }`. The tree's Add and Move controls write `_parent` for you; never declare a field named `_parent` (it is reserved and rejected).
- Seed data and scripts write the link as an object: a seeded child is `{ "id": "Task-1", "title": "Ship it", "_parent": { "id": "Epic-1", "type": "Epic" } }`, a script creates one with `publishData({type: "Task", data: {title: t, _parent: {id: id, type: type}}})` from the parent's scope (`id` and `type` there are the parent record's own). With only a bare id, pass the parent's type along with it — `byId` needs the type name, so it cannot recover one; a `_parent` with no `type` still links, but `t._parent.type` then reads nothing. A root record has no `_parent` at all.
- Formulas read the link as `t._parent.id` and `t._parent.type` — children of the record in scope: `filter($data.Task, (t) => t._parent.id == id)`; Tasks placed directly under an Epic: `filter($data.Task, (t) => t._parent.type == 'Epic')`. Reading `_parent.id` on a root record is `undefined`, not an error.
- The explicit alternative, still supported: declare ONE field whose **`type` is the literal `"parentRef"`** — e.g. `"fields": [{ "name": "title", "type": "text" }, { "name": "parentId", "type": "parentRef" }]` — and that type's records then link through `parentId` (a plain id string) INSTEAD of `_parent`. The field's TYPE is what counts, not its name. Pick one spelling per type: on a type with a `parentRef` field a written `_parent` is ignored (and a script literal doing it is rejected), and two `parentRef` fields on one type are ambiguous and rejected.
- Every declared `nodeTypes` key must be reachable from `rootType` by walking `allowedChildTypes` — an unreachable type is dead config and is flagged.
- Never emit `value` or `expanded` children on a tree. Those are builder-injected admin-designer state; a data-bound tree holds no node values and reads every row from records.
- `data.whereClause` filters ROOT records only. Descendants are always reached through their parent link, so a clause cannot prune a subtree.
- `labelField` names the record field used as the row label; omit it and the ObjectType's best name field is used. A typo degrades silently to that fallback instead of erroring, so check the name against the ObjectType's fields.
- `detail` names a node nested INSIDE the tree's own `_children` array — e.g. `{ "type": "tree", "nodeTypes": { "Task": { "detail": "taskDetail" } }, "_children": [{ "type": "content", "name": "taskDetail", "htmlTemplate": "@`…`" }] }`. This is NOT the list master-detail pattern: a screen declared elsewhere in the app (say under a `components` folder) will NOT be found, and the tree needs no cursor-linked detail screen. Omit `detail` entirely and a default form is generated from the ObjectType's fields — prefer that unless a custom layout is actually wanted.
- One level can mix types: `"allowedChildTypes": ["Epic", "Task"]` offers the user a type picker when adding a child.

## Screen node pitfalls

- The first screen child of `appConfig._children` is the home screen. Always ensure a screen sits at index 0.
- `data.dataType` must reference a name declared under `objectTypes._children`. Singular form ("Recipe", not "Recipes") is the convention.
- `layout` is optional; if set, `axis` is `"x"` or `"y"` and `mode` is `"columns"` or `"rows"`. Don't invent values.
- Screens placed under a `Components` folder are detail/edit screens (master-detail pattern). Navigate to one from a list row with a declared action that passes the record's id — `<button data-action="open" data-param-id="${id}">` plus `"actions": { "open": { "params": ["id"], "script": "navigate('taskDetail', {id: $params.id})" } }` — and resolve the record on the destination with a variable computing `@byId('Task', $args.id)`.

## Subsection node pitfalls

- `isRepeating: true` requires a `data: { dataType, source }` binding. Without it the subsection renders nothing.
- Default vertical margin between repeating subsections is set by the platform; do not add `marginBottom` manually unless you want to override.
- WHERE clauses on a subsection's `data` use `this` to refer to the iterating record (NOT `it` — that's for filter/map/reduce inside formulas).
- When a record occupies a RANGE of the parent's rows — a multi-day event across a day list, a stint across laps — use `data.span` instead of writing an equality filter. It replaces the `whereClause` you would otherwise write: `{ "type": "subsection", "isRepeating": true, "data": { "dataType": "Event", "source": "storage", "span": { "startField": "Start", "endField": "End", "axis": "@day", "mode": "repeat" } } }`. Here `axis` is a formula for the CURRENT row's position, normally the variable the parent repeating node computes per row (e.g. a `variable` named `day` whose compute is `@today() + $index`); `startField`/`endField` are fields on the bound objectType. Both must be real declared fields or the org fails validation, and a span on a node without `isRepeating: true` is rejected because there are no rows to cover.
- `data.span` is one facet of the `data` block, so it sits beside `dataType`/`source`/`sort` — NOT at the top level of the node. Do not also write a `whereClause` that matches a single slot (`@dateCompare(day, Start) == 0`): span owns row matching, and an equality clause on top would cancel it out. A `whereClause` that filters on something else entirely (`@this.published`) is fine and is applied as well.
- With `mode: "repeat"` (the default) the record renders in EVERY row it covers; read `$spanPosition` (`"start"` / `"middle"` / `"end"` / `"single"`) to style the run so it reads as one continuous element, plus `$spanStart` and `$spanEnd` for the range itself. With `mode: "once"` it renders only on the row where its run starts, which is what a plain equality filter does — pick that when one card per record is wanted, and show the range with `${$spanStart} – ${$spanEnd}`.
- `layout: { "mode": "spatial", "cols": N }` turns a subsection (or screen/app) into a 0-based CELL GRID — a seating plan, a month view, a board, a piano roll. `cols` is REQUIRED in spatial mode (the closing gate fails the org with `spatial-missing-cols` without it); `rows` is optional (omit and the grid grows downward to fit whatever is placed) and `rowHeight` (px) is optional (omit for content-sized rows; fix it when cell geometry must line up, as in a month grid). Both `cols` and `rows` accept a number or an `@`-formula evaluated in the container's scope (`"cols": "@length(sections)"`, `"cols": "@bars * 16"`). Unlike `mode: "columns"` / `mode: "grid"`, NOTHING flows by default here — each child picks its own cell through its `place` field; a child without `place` drops into the next free cell in document order, two children resolving to the same cell overlap (later paints on top, deliberately — a board square and the piece on it), and a screen narrower than the grid scrolls sideways instead of squashing.
- `place` goes on the CHILD, never on the spatial container: `"place": { "x": 2, "y": 1 }` with optional `"w"` / `"h"` cell spans (default 1). `x` and `y` are 0-based (origin top-left) and BOTH are required once `place` is present (gate error `place-incomplete`); each member is a number or an `@`-formula evaluated in the child's own scope. For a repeating child (`isRepeating: true` + `data`) EVERY ITERATION becomes its own grid item and `place` is re-evaluated per iteration from that record's fields or `$index` — so ONE repeating child carrying `"place": { "x": "@Col", "y": "@Row" }` over `SeatAssignment` records draws the entire seating plan, and `{ "x": "@$index % 7", "y": "@floor($index / 7)" }` lays 42 day cells into a 7-wide month. Out-of-range values clamp to the edge and a non-numeric result falls back to auto-flow, silently. Do NOT put `showHeader`, `collapsible` or `pageSize` on a repeating child inside a spatial parent — that chrome does not render in spatial mode and the gate warns `spatial-unsupported`; `place` on a child whose parent is NOT spatial is ignored with a `place-outside-spatial` warning.
- Complete seating plan — the smallest spatial org, one repeating child placed by its own record's fields (`SeatAssignment` records shaped `{ "Guest": "Ada", "Row": 2, "Col": 4 }`; an empty seat is simply an unoccupied cell): `{ "id": "subsection-1", "type": "subsection", "name": "seatMap", "layout": { "mode": "spatial", "cols": 10, "rows": 6, "rowHeight": 48, "minColumnWidth": 40 }, "_children": [ { "id": "subsection-2", "type": "subsection", "name": "seats", "isRepeating": true, "place": { "x": "@Col", "y": "@Row" }, "data": { "dataType": "SeatAssignment", "source": "storage", "sort": { "field": "Row", "direction": "asc" } }, "_children": [ { "id": "content-1", "type": "content", "name": "seatChip", "htmlTemplate": "@`<div style=\"height: 100%; display: flex; align-items: center; justify-content: center; border-radius: 6px; background: #e3f2fd; font-size: 12px;\">${Guest}</div>`" } ] } ] }`. Note the shape: `layout` (with `cols`) on the OUTER subsection, `place` + `data` on the INNER repeating subsection, and the visual in a `content` child that reads the record's fields (`${Guest}`) as bare identifiers.
- To read per-row user edits back out of a repeating subsection (a save script, a live tally), use **`$rows('subsectionName')`** — it returns each row's record merged with its inputs, input-over-record. A bare reference to the subsection name merges record-over-input, so a per-row input named like a bound field is silently shadowed (the "edited value reads back as the original / live tally reads 0" trap). Bulk-save the whole set in one step: `publishData({type: "X", data: $rows('rows').map((r) => ({...}))})`.

## List node pitfalls

- `MasterDetail`-style lists pair a list with a detail screen via the cursor. The detail screen's pointer must match the list iteration's pointer.
- Sort options (`data.sort`) accept a single field; multi-field sorting is not supported.
- A list with `data.source: "embedded"` requires sample instances under `objectInstances._children`. Without them the list renders empty.

## Repeat node pitfalls

- Use a `repeat` when a flow must ask the SAME questions once per item and the user decides how many ("Add another guest?"). Never ask for a count up front and never fake it with numbered screens: the repeat draws the summary (one row per item with Edit and Remove, "Add another", Done) for you.
- A `repeat` is a DIRECT child of a `flow`, and its children are `screen` nodes, one per page of a pass. Inputs go inside those screens. No repeat inside a repeat. The gate rejects each of these shapes.
- Worked example, a guest list inside a booking flow: `{"type": "flow", "name": "booking", "_children": [{"type": "screen", "name": "who", "_children": [{"type": "textInput", "name": "lead", "label": "Your name", "required": true}]}, {"type": "repeat", "name": "guests", "label": "Guests", "itemLabel": "guest", "summary": "@guestName + (diet ? ' · ' + diet : '')", "min": 1, "max": 8, "_children": [{"type": "screen", "name": "guestScreen", "_children": [{"type": "textInput", "name": "guestName", "label": "Guest's name", "required": true}, {"type": "textInput", "name": "diet", "label": "Dietary needs (optional)"}]}]}, {"type": "script", "name": "save", "script": "publishData({type: \"Booking\", data: {lead: lead, guests: guests}}); navigate(\"thanks\")"}]}`
- After the repeat, its NAME reads as an array of per-pass objects with every screen's inputs merged flat: `guests` is `[{guestName, diet}, …]`. Build the record from it in a later `script` step (pure `map`/`reduce`, then ONE host call — host calls inside a loop are rejected).
- Input names must be unique across ALL of one repeat's screens, because a pass's screens merge into one object. They may repeat names used outside the repeat.
- `summary` is plain text evaluated in each pass's scope, so the pass's inputs are bare names (`@guestName`), and `$index` is the pass number (0-based). Keep it to one short line.
- `itemLabel` is the lower-case noun ("guest"); the platform capitalises it where needed ("Guest 2 · 1 of 1", "Add another guest"). It may be a formula reading an earlier step.
- `min` gates Done (a pass only counts once every `required` input on its screens is filled and every `validation` rule passes); `max` hides "Add another". Both take a number or a formula.
- Next refuses to leave a screen (any flow screen, including a pass's) while a `required` input is empty, marking it red, so mark the fields a pass genuinely needs as `required`.

## Flow node pitfalls

- A flow's `_children` are its steps, in order: `screen` nodes (a page of inputs), step nodes written by their own type (`{"type": "script"}`, `{"type": "aiQuery"}`, `{"type": "transcribe"}`, …) and `repeat`. Never write `"type": "flowStep"` or a builder name like `scriptStep`: the step's type IS its kind, and `scriptStep` fails as an undeclared plugin.
- Give a flow at least one `screen` step. A flow whose every step is a `script` gives the user nothing to fill in: they tap in, then tap its one button. Run that script from the button itself instead, as a declared content action (`<button data-action="start">` + `actions: {start: {script: "…"}}`, with `confirm` for a destructive one). The gate warns `flow-script-only`.
- Next and Finish refuse to leave a flow screen while a visible `required` input is empty or a `validation` rule fails; the fields turn red. Mark what the step genuinely needs as `required` instead of checking it in the script. Hidden inputs never block.
- A step whose `hidden` formula is true drops out of the flow entirely: it leaves the stepper and never runs. Use it to gate an action (`hidden: "@!roomExists"` on a `script` step means finishing writes nothing until the room exists) or to give one flow two paths (an AI step and a pick-from-list step, each hidden when the other applies).
- A `script` step runs as soon as it is entered, and its value is readable later as `<stepName>.result` (the value of its last expression), so a script can load data a following screen shows: `{"type": "script", "name": "loadPlaylists", "script": "spotifyListPlaylists()"}`, then `"pickerValues": "@loadPlaylists.result"` on that screen's `selectInput`.
- To pass a value INTO a flow, open it from a declared action whose script calls `navigate` with an args object (`<button data-action="add" data-param-day="${day}">` + `actions: {add: {script: "navigate('newEvent', {Start: $params.day})"}}`), then read `$args` inside the flow: `"compute": "@($args.Start ? $args.Start : '')"` on an input, or `$args.Start` in a `script` step. Never use `param=`, which a flow cannot see.
- `autoAdvance` on a step is a plain `true`/`false`, never a formula: `"autoAdvance": "@true"` passes validation and then fails to publish. `hideTopBar` and `hideNav` on the flow DO accept a formula.
- With `hideNav: true` the flow has no Next button, so a step advances only when your own content calls `advanceFlow()` (a declared action's script). Pair it with `hideTopBar: true` for a one-screen form that should look like a plain screen.
- A flow's inputs reset every time the flow is navigated to; a plain screen's inputs keep whatever was typed last. So an edit form opened per record (`navigate('editRole', {id: $params.id})`) belongs in a one-step flow with `hideNav` and `hideTopBar`, or record B opens showing record A's typing.
- To ask the same screens once per item ("Add another guest?"), use a `repeat` step; call `get_node_schema("repeat")` for its shape and rules rather than numbering screens.

## Form node pitfalls

- `form` is LEGACY: never add one to a new org. Put the inputs straight on a `screen` (or a flow screen) and save them with `publishData({type, data: {…}})` / `updateData` in a script, naming each input in `data`. The bullets below are for reading or editing an org that already has a form.
- A form must have a `formConfig` whose `dataType` matches an entry in `objectTypes`. The form fields are derived from that type's fields.
- `formConfig.scope` controls where submissions are written: `"global"`, `"user"`, `"variant"`, or `"all"`. Variant-scoped publishing is admin-only — the form publish path rejects it.
- Public auth mode (`authMode: "public"`) disables the publish button for `scope: "user"` forms when no user is signed in. Show inline helper text rather than auto-creating an anon user.

## Text input node pitfalls

- `variant` is `"basic"` (default) or `"multiline"`. Number input is a separate node type (`numberInput`).
- `placeholder` and `label` are static strings or formulas. Do not put HTML in either.
- Input values stored under the iteration's pointer key; reference them with `value.<fieldName>` from sibling nodes.

## Select input node pitfalls

- The choices go in `pickerValues`, never `options`. Each is a plain string (`["Small", "Medium", "Large"]`), or an object `{id, label}` when the stored value differs from the text shown; add `group` to divide a long list. The input's value is the string, or the picked option's `id`.
- A select input has no `dataType`. To offer records, map them in a formula: `"pickerValues": "@filter($data.Team, true).map((t) => ({id: t.id, label: t.name}))"`, which stores the picked record's `id`.
- It picks ONE value. There is no `multi` field, and `variant: "multiple"` passes validation but still renders a pick-one dropdown, so for "pick any of these" write one `booleanInput` per choice.
- `idiom` sets the look: `"select"` (the default dropdown), `"radio"` for two to four choices, `"combobox"` (type to filter) for a long list.

## Content node pitfalls

- `htmlTemplate` strings start with `` @` `` (backtick after `@`). Template literals use `${expression}` for formula interpolation. Do not use plain backticks without `@`.
- For cross-org links (`<a href="orgiggly.com/<slug>">` or `<a href="/<slug>">`), include `target="_blank"` or the SPA router intercepts the click.
- Raw `<img src="...">` has no onError fallback. For dynamic image URLs, conditionally render or use a default URL when the source might 404.
- Inline `<style>` tags only work at screen level via a content node, not inside per-node htmlTemplates.
- Clicks have exactly TWO channels: a real `href` for a genuine hyperlink (`http(s):`, `mailto:`, `tel:`, `/`-absolute), and `data-action="<name>"` for every behaviour. Do NOT emit `rel=`, `setValue=`, `param=`, `data-script`, `data-args`, `data-speak*`, `href="@pop"` or `href="@submit"` — those are frozen legacy channels that you will see in existing orgs but must not write in new ones.
- The full shape of an `actions` entry: `"actions": { "openTask": { "params": ["id"], "script": "setAppValue('lastOpened', $params.id); navigate('taskDetail', {id: $params.id})" } }`. `params` declares the names bound from `data-param-*`; `script` runs with `$params` in scope. Navigation is a host call in the script — `navigate('screen', args?)` pushes (adds a back step), `replaceScreen('screen', args?)` swaps the current screen, `back()` goes back — normally as the LAST statement, so an earlier failure aborts it. A Back or Cancel button is `{ "script": "back()" }` and needs nothing else.
- Bind params as render-time interpolations: `data-param-id="${id}"`, never `data-param-id="id"`. Click-time dispatch evaluates no formulas, so the attribute must already hold the literal value. HTML lowercases attribute names, so a param declared `taskId` must be bound as `data-param-taskid` — prefer all-lowercase param names to avoid the mismatch entirely.
- Put `data-action` on a `<button>`, not an `<a>`. Reset the button chrome in the style attribute (`border: none; font: inherit; cursor: pointer;` plus `text-align: left; width: 100%;` for a card) or it will not match the surrounding UI.
- To hold state in a content node, give it a `compute` for the initial value and have an action's script call the `setValue(…)` host function. Read the value back by the NODE'S OWN NAME, in the template and the script alike — there is no `value` variable, so a bare `value` is undefined (`value.index` renders `NaN`). E.g. a node named `tagFilter`: `{ "name": "tagFilter", "compute": "@[]", "actions": { "toggle": { "params": ["tag"], "script": "setValue(tagFilter.includes($params.tag) ? tagFilter.filter((x) => x != $params.tag) : [...tagFilter, $params.tag])" } } }`. This is the filter-UI pattern; `setValue`, `speak`, `stopSpeech` and `submit` are host functions available only inside an action's script.
- A content node's stored value beats its `compute` for good. Once the visitor types into an `<input>` in its template, or a script calls `setValue`, the value is kept on their device and `compute` is never read again: across reloads and days, and even after what `compute` reads has changed. A daily app's answer box showed yesterday's answer every day this way. So clear the value once it has been used: end the save action's script with `clearValues('<node name>')` (e.g. `publishData({type: 'Answer', data: {text: answer}}); clearValues('answer')`), and `compute` applies again. No screen-enter hook resets it. To drop values already stored on devices after a fix, rename the node; nothing else reaches them.
- Identify records by id, not list position: bind `data-param-id="${id}"`, pass it as `navigate('taskDetail', {id: $params.id})`, and resolve it on the destination with a variable whose compute is `@byId('Task', $args.id)`. A destination that reads the clicked row's scope only works from that one list; one that reads `$args.id` works from every entry point, including a deep link.
- Inside a spatial container (a parent with `layout: { "mode": "spatial", "cols": N }`) a content node may carry `place` DIRECTLY — `{ "id": "content-3", "type": "content", "name": "stageLabel", "place": { "x": 2, "y": 1 }, "htmlTemplate": "@`<div>Stage</div>`" }` — to pin a static label, a legend, a header cell or a board square at a 0-based `(x, y)` cell, with optional `w`/`h` spans (`"w": 3` stretches it across three columns). Both `x` and `y` are required once `place` is present (gate error `place-incomplete`), each may be a number or an `@`-formula evaluated in this node's scope, and siblings WITHOUT `place` auto-flow into the next free cell in document order, so a fixed title cell and auto-flowed tiles mix freely in one grid. `place` on a content node whose parent is not spatial does nothing (gate warning `place-outside-spatial`) — the parent's `layout.mode` is what activates it.
- An action name used by `data-action` must exist in `actions`, or the closing gate fails the org. A declared action the template never invokes is a warning, as is a `data-param-*` binding whose name is not in the action's `params`.

## Plugin node pitfalls

- A plugin's `name` becomes the node `type` for invocations. Reference plugins as `{ type: "<name>", parameters: { ... } }`.
- `parameters` declared on the plugin definition must match the keys passed at invocation. Missing parameters render as `undefined`.
- Inside a plugin's `htmlTemplate`, reference parameters as `${parameters.<name>}`.
- Cross-org link plugins need `target="_blank"` in their anchor; without it the SPA intercepts.

## Script step node pitfalls

- The `script` field is a RAW statement sequence — no `@` prefix. Statements are `;`-separated; assignment (`x = expr`) is supported.
- **A ternary as a whole STATEMENT swallows the statements after it** — `cond ? a : b; publishData(...)` parses the publish into the alternate (nested → rejected). Assign it instead: `x = cond ? a : b;` binds the whole ternary to `x` and ends at the `;`, as does `x = a || b` / `x = a ?? b`.
- Async host calls (`publishData`, `updateData`, `deleteData`, `setAppValue`, `navigate`) are only legal as a whole statement or as the RHS of an assignment — never nested inside another expression or another host call's arguments. Bind intermediate results to variables first.
- There are no `if` statements — but you cannot branch around host calls with ternaries either (that nests them). Use separate flows for create vs edit (publishData vs updateData).
- End with `navigate("<screenName>")` or the flow's last step stays selected after saving.

## AI chat step node pitfalls

- An aiChat step is a multi-turn CONVERSATION, not a one-shot query: the assistant speaks first, the user replies (typed, by voice, or by tapping a steering chip), and the two alternate until the user taps Done or `maxUserTurns` is reached. Use it when the interaction is a dialogue (a tutor, an interviewer, a coach, a guided reflection); use `aiQueryStep` when one prompt should produce one structured answer.
- The ONLY valid parent is a `flow`. An aiChat step placed directly on a `screen` or inside a `subsection` does nothing — put it in a `flow` alongside the `screen`s that collect its inputs and the `script` step that saves its result.
- The assistant opens FIRST, from `promptTemplate`. The user NEVER sees the brief — only the assistant's opening turn — so write it as instructions TO the assistant: who it is, who the user is, what to do, how long a turn should be, and how each turn should end. A brief written as a message to the user ("Welcome! Let's practise French") reads to the model as a line it must respond to and produces a confused opener.
- `promptTemplate` is a backtick template — `"@\`…\`"` — so values from earlier steps in the same flow interpolate: `"promptTemplate": "@\`You are a warm ${lang} tutor. The learner wants to practise: ${topic}. Speak mostly in ${lang}, keep turns to 2–3 sentences, and end each turn with a question.\`"`. A plain string with no `@` is used verbatim and cannot interpolate. An absent or empty `promptTemplate` is a gate warning (`aiChat-missing-prompt`): the step still runs, but on a model improvising its own persona.
- `steeringChips` is a JSON array of strings INSIDE a backtick template, parsed by the step — `"steeringChips": "@\`[\"Slower please\", \"Explain that in English\", \"Give me a harder one\"]\`"`. Do NOT write a bare array formula (`"@[\"Slower please\", …]"`) — the field is a string, so the array fails the decode and the chips silently vanish. This is the same idiom as `aiQueryStep.mockResults`.
- Tapping a chip sends its text as the user's turn; mid-stream it interrupts the assistant and re-steers it. Chips are the cheapest way to give a non-typing user (a language learner, a child, someone on a phone) a way to drive the conversation — offer three or four short ones, phrased as things the USER would say.
- `mockReplies` uses the same shape as `steeringChips` — a JSON array of strings inside a backtick template, one assistant reply per turn: `"mockEnabled": true, "mockReplies": "@\`[\"Bonjour ! Comment ça va ?\", \"Très bien. Et maintenant…\"]\`"`. When the array runs out the mock repeats its last reply. `mockEnabled: true` skips the AI entirely (no credits) but runs the full stop/steer/Done machinery, so a flow can be checked end to end before it costs anything. Leave both off for the real thing.
- `speakReplies: true` reads each assistant sentence aloud as it streams, using the device's own Web Speech voices. For ANY language other than the device default, also set `speechLang` — a BCP-47 tag (`"fr-FR"`, `"cmn-Hans-CN"`), an English language name (`"Mandarin Chinese"`), or a formula reading an earlier input (`"@lang"`). Without `speechLang` a French lesson is read in an English voice.
- `speechLang` is only read when `speakReplies` is on. Setting `speechLang` with `speakReplies` absent or `false` is a gate warning (`aiChat-speech-lang-unused`): the author plainly wanted spoken replies and gets silence. Either set `"speakReplies": true` or remove `speechLang`. A formula `speakReplies` (`"@wantsVoice"`) is accepted as is.
- `voiceInput: true` adds a mic button to the reply row: the recording is transcribed and sent as the user's turn. The transcript, not the audio, enters the conversation. Pair it with `speakReplies` for a hands-free spoken lesson; it works fine alone for a user who would rather talk than type.
- The step stays `running` until the user taps Done (or the turn cap is hit). Do NOT set `autoAdvance: false` expecting a pause — completion already waits on the user, and the flag only controls whether the flow moves to the NEXT step once this one completes. Leave `autoAdvance` alone on an aiChat step; put `"autoAdvance": false` plus an `actionLabel` on the FOLLOWING `script` step if the user should confirm before the save.
- `maxUserTurns` caps how many user turns the conversation allows — 1 to 100, default 20 — and is the one number that bounds the step's cost, stored transcript size and the model's context. Hitting the cap behaves exactly like tapping Done. Pick it from the register: a quick check-in is 4–6, a lesson 10–15; a literal outside 1..100 is a gate warning (`aiChat-turns-range`). A formula (`"@turns"`) is allowed and not checked.
- `.result` on Done is `{ text, turnCount }` — `text` is the full transcript as one string, `turnCount` the number of user turns. Set `typeDescription` to have a final extraction pass distil the finished conversation into that shape instead: `"typeDescription": "@\`{ summary: string; // 2 sentences, in English\n  vocabulary: string[]; // new words the learner met\n  corrections: { said: string; better: string }[] }\`"`. Inline `//` comments after each field steer the extraction; it costs one extra non-streaming AI call.
- `resultObjectType` names a MetaModel object type and only SEEDS a default `typeDescription` — it does not constrain the AI by itself. Name the type the result will be saved as (`"resultObjectType": "Session"`) and write `typeDescription` when the shape matters.
- Save the result from a following `script` step, spreading the distilled object into a record: `{ "type": "script", "name": "save", "autoAdvance": false, "actionLabel": "Save this session", "script": "publishData({type: \"Session\", data: {...tutor.result, language: lang, at: $now}})" }`. The step is referenced by NAME (`tutor.result`), so give the aiChat step a short, meaningful `name`.
- The live conversation is formula-visible while it runs: `<stepName>.chat.turns` is the transcript so far (an array of `{ role, text }`), and `<stepName>.chat.partialText` is the assistant's in-flight streaming text. A sibling `content` node in the same flow can render either — a running word count, a "turn 3 of 12" caption — but the step renders its own transcript, so do not rebuild the chat UI by hand.
- `model` is admin-only and billing-coupled — do NOT emit it. The step defaults to the platform's text model; leave the field out of every generated node.
- `inputPlaceholder` is the hint in the empty reply box, a backtick template like the other text fields: `"inputPlaceholder": "@\`Say what comes to mind…\`"`. Use it to tell the user what KIND of reply is wanted ("Answer in French, however roughly").
- A complete, minimal node: `{ "type": "aiChat", "name": "interview", "label": "Reflect", "promptTemplate": "@\`You are a thoughtful journaling companion. Ask one short question at a time about the user's day — feelings, one highlight, one difficulty. After 3–4 exchanges, tell them you have enough for their entry.\`", "typeDescription": "@\`{ title: string; entry: string; // first person, warm, ~120 words\n  mood: string }\`", "maxUserTurns": 6, "inputPlaceholder": "@\`Say what comes to mind…\`" }`. Everything else (`steeringChips`, `voiceInput`, `speakReplies`, `speechLang`, `mockEnabled`) is opt-in.

## AI query step node pitfalls

- An aiQuery step is a ONE-SHOT structured query: one prompt in, one JSON object out, no conversation. Use it to turn inputs (typed answers, a photo) into a record — a recipe, a receipt, a plant profile. Use `aiChatStep` when the user should talk back and forth with the AI instead.
- The config type is `"type": "aiQuery"` — `{ "type": "aiQuery", "name": "extract", … }`. Do NOT write `"type": "aiQueryStep"`: that is the schema/builder name, not a config type, and it fails the closing gate with a misleading "Plugin `aiQueryStep` not declared in plugins". The long form `{ "type": "flowStep", "variant": "aiQuery" }` also validates but is not how configs are authored — always write the short form.
- The ONLY valid parent is a `flow`. Put it in a `flow`'s `_children` between the `screen` that collects its inputs and the `screen` that shows its result: `screen (inputs) → aiQuery → screen (result) → script (save)`. Placed directly on a `screen` or in a `subsection` it never runs.
- `promptTemplate` is a backtick template — `"@`…`"` — so earlier inputs in the same flow interpolate by bare name: `"promptTemplate": "@`You are an inventive home chef. Design ONE recipe using: ${ingredients}. The cook has ${minutes} minutes.`"`. A plain string with no `@` is sent verbatim and cannot interpolate. Write it as a full brief to the AI (role, task, constraints), not a one-liner.
- `typeDescription` is what actually constrains the output — a TypeScript-ish shape inside a backtick template, with an inline `//` comment after each field to steer its value: `"typeDescription": "@`{\n  name: string; // catchy recipe name\n  minutes: number; // total time\n  steps: string[]; // one instruction each\n}`"`. Always write it; without it the AI invents its own shape and the result screen's references resolve to nothing.
- The result (`<step>.result`) is ONE value shaped exactly as `typeDescription`: an object type gives an object, a list type gives the whole list — `"typeDescription": "@`{\n  title: string;\n  artist: string;\n}[] // 10 songs`"` makes `<step>.result` a 10-item array, no wrapper object needed. An object type may still carry lists in its fields (`{ songs: {...}[]; title: string }`).
- `resultObjectType` names an object type and only SEEDS a default `typeDescription` — it does not constrain the AI by itself. Set it to the type the result will be saved as (`"resultObjectType": "Recipe"`) and still write `typeDescription` when the shape matters.
- The parsed object is read by the step's NAME plus `.result`: `extract.result.merchant`, `${extract.result.total}` inside a later template. Give the step a short, meaningful `name` — it is an identifier every later node uses.
- It inherits these `flowStep` fields, which its own schema does NOT list: `autoAdvance` (default `true` — move to the next step as soon as the query returns), `actionLabel` (the run button's text), `idleTitle` / `idleDescription` (shown before it runs — worth setting, because the step costs credits), `runningTitle` / `runningDescription` (shown while it runs). All are backtick-template strings except `autoAdvance`: `"idleTitle": "@`Read the receipt`", "idleDescription": "@`Sends your photo to the AI to pull out the details.`", "actionLabel": "Read it"`.
- VISION: set `imageSource` and the step sends image(s) along with the prompt. It is a formula naming an image `fileInput` in the same flow by bare name — `"imageSource": "@photo"`. Also accepted: `"@photo.url"`, a `multiple: true` fileInput's array (`"@photos"`, up to 8 images; non-image files are skipped), or an earlier imageGenerationStep's picture — a flow step's value needs `.result`, so `"@generated.result.url"`, never `"@generated"`.
- VISION: the name in `imageSource` must be a node that exists, or the gate reports `vision-source-unresolved` — the step would run with no image and the AI would answer from the prompt alone. Match it character for character to the fileInput's `name`.
- VISION: the image does not replace the output contract — a vision query still needs `promptTemplate` (what to look for) AND `typeDescription` (what to return). `"promptTemplate": "@`Read this receipt. Report amounts exactly as printed; if a value is illegible, use null rather than guessing.`"`.
- VISION: pair it with a `fileInput` whose `"variant": "image"`, in a `screen` BEFORE the aiQuery step. The user picks or shoots a photo and taps Commit to upload it; until then `@photo` is empty and the step shows "Add a photo first" instead of running. Leave `showCommit` at its default.
- VISION: uploads are re-encoded to an 800px-wide JPEG unless the fileInput says otherwise, which loses fine print. For anything with TEXT in it (a receipt, a label, a menu, a whiteboard) set `"imageOutputOptions": { "width": 1568, "format": "jpeg" }` on the fileInput — the gate warns `vision-low-fidelity-source` otherwise. For identifying a whole subject (a plant, a dish, a dog) the default is fine and the warning can be left.
- `model` is admin-only and billing-coupled — do NOT emit it. Every query runs on the platform's default text model, which reads images; leave the field out of every generated node.
- `mockEnabled: true` skips the AI (no credits) and returns `mockResults`, a JSON string inside a backtick template: `"mockEnabled": true, "mockResults": "@`[{\"merchant\": \"Corner Café\", \"total\": 12.5}]`"`. Leave `mockResults` out to have mocks generated from `typeDescription`. Leave both off for the real thing.
- Save the result from a following `script` step, spreading the object into a record: `{ "type": "script", "name": "save", "autoAdvance": false, "actionLabel": "Save expense", "script": "publishData({type: \"Expense\", data: {...extract.result, at: $now}}); navigate(\"expenses\")" }`. Show the result on a `screen` between the two so the user can check it before saving.
- A complete vision flow: `{ "type": "flow", "name": "scanFlow", "label": "Scan a receipt", "_children": [ { "type": "screen", "name": "shoot", "label": "Photo", "_children": [ { "type": "fileInput", "name": "receiptPhoto", "label": "Receipt", "variant": "image", "imageOutputOptions": { "width": 1568, "format": "jpeg" } } ] }, { "type": "aiQuery", "name": "extract", "label": "Read receipt", "imageSource": "@receiptPhoto", "promptTemplate": "@`Read this receipt. Report amounts exactly as printed; use null for anything illegible.`", "typeDescription": "@`{\n  merchant: string;\n  date: string; // YYYY-MM-DD\n  total: number; // grand total incl. tax\n  items: { name: string; price: number }[];\n}`", "resultObjectType": "Expense", "idleTitle": "@`Read the receipt`", "actionLabel": "Read it" }, { "type": "screen", "name": "check", "label": "Check", "_children": [ { "type": "content", "name": "extracted", "htmlTemplate": "@`<h3>${extract.result.merchant}</h3><p>${extract.result.date} — ${extract.result.total}</p>`" } ] }, { "type": "script", "name": "save", "autoAdvance": false, "actionLabel": "Save expense", "script": "publishData({type: \"Expense\", data: {...extract.result, at: $now}}); navigate(\"expenses\")" } ] }`.
