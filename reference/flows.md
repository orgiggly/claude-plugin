# Org flows & flow steps — the authoring contract

Two audiences, one contract. For a **flow-container developer** (`Flow.tsx`,
`FlowStep.tsx`, `useFlowStepExecution.ts`) this is the behaviour org configs
already depend on — breaking a line here breaks shipped orgs. For an **org
config author** this is the flow half of `org-config.md`, extracted in #2055 so
it no longer auto-loads on every `config.json` edit; reach it from that file's
headline index.

`web-flows.md` covers the same directory from the implementation side (step
variants, script host fns, file capture, Storage paths). This file is only the
authoring-visible contract.

## Step types, entry and self-running

- **In a config FILE a flow step is authored as its variant: `{"type": "aiQuery"}`, `{"type": "transcribe"}`, `{"type": "script"}`, … — the one rule for every variant family (`tab`/`tabGroup`/`folder` are the same rule on `appNode`).** `designToAppDef` maps it to the runtime `{type: "flowStep", variant}`; that raw pair is still ACCEPTED from old data but nothing writes it and no prompt shows it (#2090). `aiQueryStep`/`transcribeStep`/`scriptStep` are BUILDER and codegen names, not config types: using one fails the references stage with `Plugin \`transcribeStep\` not declared in plugins`, which reads as a missing plugin rather than a wrong type name. (#652)

- **A step can repeat: `{"type": "repeat", "itemLabel", "summary", "min", "max", "_children": [screens]}` asks its screens once per item, and the platform draws the "Add another / Edit / Remove / Done" summary.** Each pass is an iteration (`roles[0]`), so a later step reads `roles` as `[{…every screen's inputs flat…}]`, and `$index` inside a pass is the pass number. A direct flow child only, screen children only, no nesting, input names unique across its screens — the gate refuses each. `node-pitfalls/repeat.md` has a worked example. (#2383)

- **On ANY flow screen, Next/Finish/`advanceFlow()` refuse while a visible `required` input is empty or a `validation` rule fails: the fields turn red ("Required"), the first scrolls into view, and a line under the nav says "Fill in the fields marked in red".** Next stays enabled on purpose — pressing it is what tells you what's missing. Hidden inputs never block. Before this a flow's Next ignored `required` entirely (forms still don't gate). (#2384 follow-up)

- **A flow with no screen step is a one-tap action in disguise — use a declared content action instead.** A flow whose only step is a `script` can never self-run (`autoRun` only flips once the user advances a step), so the user taps "Start the game", lands on a screen holding nothing but "Start now", and taps again. Six games shipped Start/Leave/Play-again that way, copied from each other; it is now one tap via `<a data-action="start">` + `actions: {start: {script: …}}` on the button itself, with `confirm: {title, body, ok, cancel, destructive}` for a destructive one like a mid-game Leave (Bandwagon is the reference). Move any useful `idleDescription` text under the button. The `flow-script-only` rubric warning flags the pattern. A flow earns its place when it has a screen to fill in (create-room's name step). (#2206 follow-up)

- **The flow chrome is a centred ≤640px column in the org's `themeColors.accent`: the stepper shows only past two visible steps, Next/Finish are the filled accent button, every button inside is sentence case.** So an org with no `accent` gets the platform cyan on its flow and its inputs — set the accent before judging how a flow looks. A step hidden by `hidden:` doesn't count toward the stepper threshold. (#2206 follow-up)

- **`autoAdvance` is a plain `boolean` (no `|string`), and `validate-org` passes a formula there while `create-org`/`update-org` reject it.** `autoAdvance: "@true"` validates clean, then the tree→pointer conversion dies with `Invalid value at 1.autoAdvance`. Treat a clean validator as necessary, not sufficient — codec-level type errors only surface at publish. (`flow`'s `hideTopBar`/`hideNav` ARE `boolean|string`, so a formula is fine there.)

- **A flow entered by a direct `?r=<flow>` URL keeps its previous completed/errored state and won't re-execute; entering via a link resets it.** So an iteration loop that navigates straight to a flow silently re-tests nothing — the step just shows "— completed" from last time. Enter through the app's own link (or CANCEL first) between runs, or you'll attribute a stale pass/fail to the change you just published. Script errors DO surface in the step panel, so a genuinely re-run step that fails will say so.

- **Gate a flow's `flowStep:script` action on a reactive condition with `hidden: "@!cond"` — a hidden script step is FILTERED from the flow, collapsing the step count, and is never entered so its script never auto-runs.** The clean "only let them act when X" pattern: when `cond` is false the flow collapses to a single step whose nav button becomes **Finish**, and finishing runs NO script, so no side-effect record is written; when `cond` flips true the step reappears. Squiggly gates `stepDoJoin` on `@!roomExists` so a bogus room code can't strand a Player. Two facts this leans on: a **`flowStep:script` auto-runs on entry** (so an E2E must try-click the idle action with a timeout and tolerate its absence), and a sibling **`variable` + a `maxLength: "@0"` realtime probe** is how you get a reactive existence check. (#1178)

- **A `script` step's value is ALSO `<step>.result` — the value of its last expression — so a script step can load data a later screen step renders.** intro-quiz's `loadPlaylists` is just `spotifyListPlaylists()`, and the next screen's `selectInput` reads `pickerValues` from `loadPlaylists.result`. Pair it with `hidden` on each step to give one flow two paths (AI vs playlist): a hidden step drops out of the stepper and never runs. In a pack, a `setValues` stub must send `undefined` to `p.clearValue(k)`, since the web clears on `undefined` and `p.setValue` would store it. (#2480)
- **An `aiQuery` result is ONE value shaped exactly as its `typeDescription` (#2482): a list type (`{…}[]`) gives `<step>.result` as the whole list, an object type an object.** No wrapper object is needed for a list any more; configs written before #2482 wrap one (`{ songs: {...}[] }`) and still work. An object may carry scalars beside its list (intro-quiz's `{ songs, title }`), but if the model sends only the bare list the platform files it back under the list field and the scalars are lost, so give each one a fallback.
- **`aiQuery` steps are auth-gated even with `mockEnabled: true`** — an anonymous session sees the platform "Sign in to continue" gate instead of the Run button, so a public org's AI-flow back half can't be verified anonymously on prod. Verify what renders pre-gate; the rest needs a real signed-in run.

## Passing data into a flow

- **Passing data into a FLOW on navigation: `data-args` → `$args`, never `param=`.** `param=` stores the value at the destination pointer, which only Forms consume as their record; flow-input computes can't see it. Use `<a rel="newEvent" data-args="{Start: '' + day}">` (evaluated at click time in the ROW scope, where iteration variables resolve) and read it with `compute: "@($args.Start ? $args.Start : '')"`. Referencing the row's variable directly from a flow input re-evaluates its `@today() + $index` compute with `$index` undefined → `"2026-06-06undefined"`.

- **A sole `flowStep:script` CAN read `$args` — so a per-row link can run a parameterized one-tap action with no input-screen step.** `$args` resolves via `selectCursorArgs` (already in `KNOWN_SPECIAL_VARS`), and a flow's internal step is a stored *value*, not a cursor push, so the cursor stays on the flow screen with its `data-args` intact while the script runs. Pattern: `<a rel="viewRevealFlowScreen" data-args="{code: '' + rows[$index].id}">` → `script: setAppValue("roomCode", $args.code); navigate("reveal")`. The webberoonies input-`compute: "@$args.x"` pattern is the equivalent that adds a Next-tap — use it as the fallback.

- **A `flow` step input named the same as a field of the flow's entry-scope record now persists correctly (engine fix #799) — the old renaming workaround is unnecessary.** Previously a step input named identically to a record field (`Bio`) was shadowed: at Finish the script's `patch: {Bio}` resolved to the *original* record field via `getDataFallback`, a stale write with no error. `getDataFallback` now prefers a stored value at the field's canonical pointer, so same-named inputs + object-shorthand patches just work. Distinct names remain a fine stylistic choice.

## Writing data from a `flowStep:script`

- **All `publishData` calls in one `flowStep:script` share a single `$data` snapshot** (the eval context is built once at script start), so two writes to the same record id clobber — the second never sees the first's write. Emit at most one `publishData` per id, pre-merging: `old = filter($data.X, it.id == …)[0] || ({})`, then write the full object. Intermediate results bound to a variable (`post = publishData(...)`) ARE visible; only `$data.X` is stale.

- **To write a whole nested record in a script while dodging the async-host-in-loop ban, BUILD the object with pure formula ops and emit it in ONE host call.** `evalScriptAsync` only forbids host calls *inside* loops (`reduce`/`times`/`map`), not pure object-building — and the engine supports object spread, computed keys, `reduce` into an object accumulator, and `times`. So Squiggly's whole `Game` is `books = reduce(...); deal = reduce(...); setRealtime("Game/"+code, {...})`: one host call, no CF change. Two parse traps: parenthesise a ternary on an assignment's right-hand side (`id = (a ? a : "x" + b);` — unparenthesised, the `;` lands in the else branch and the next host call reads as "nested inside another expression"), and bind `generateId()` to a variable before using it in an expression. (#2176)

- **A script that `publishData`s a new record then immediately `navigate`s to a screen reading it via `byId` gets a blank first paint** — the destination's lookup only sees the record after an async refetch, not synchronously off the local write. Guard the template with a ternary on the looked-up variable: real card when truthy, "Saving…" when falsy; it self-heals once the refetch lands. Reference: `content-myFounderHeader` in `orgs/dave/pairing-desk/config.json`.

- **In a `flowStep:script`, prefer `let name = expr;` for locals — immutable, visible to every later statement and to lambdas written there, and it never flushes the function-call memo.** The older claim that plain assignments "don't survive to the next statement" was wrong as a mechanism: they do, and the one reproducible trap (a binding whose value was `undefined` fell through to the enclosing scope's name) was fixed in #1858. Still parenthesise a ternary or arrow initialiser after a plain `=` (`x = (c ? a : b);`) — `let` re-associates both for you. (dave/whipround, #1858)

- **Don't reference scope-dependent screen `variable` nodes from a `flowStep:script`.** A variable whose compute uses rel-inherited iteration scope (`@'pred-' + groupKey + '-' + userKey`) evaluates with the scoped identifier **undefined** in the script context, while the same bare identifier resolves fine inside the script itself. Inline the expression, or use explicit-arg `function` nodes.

## Inputs & pickers

- **A `selectInput` picker flow is a WORKAROUND, not the idiom — a record's own card can be the control, as a DECLARED action.** `<a data-action="pick" data-param-id="${id}">` + `actions.pick.script: setAppValue("curTabId", $params.id); navigate("tabHome")` does "pick this record, act on it, go there" in ONE tap on a plain screen, no flow; `data-param-*` are render-time literals read as `$params`. Rows built inside a function or a `join(map(...))` work the same, at the cost of a validate-org "declared but never referenced" warning (the template gate cannot see them) — cover the script in the org pack via `runScriptAt(node, hosts, script, { $params })`. `data-script` is now flagged legacy. whipround shipped four picker flows because a bullet here wrongly declared row→detail impossible; grep `orgs/**/config.json` before recording an impossibility. (#1211, #2176)

- **A static picker list shared by several `selectInput`s belongs in ONE app-level `variable` holding an array of object literals** — `compute: "@[{id: \"£\", label: \"£ Pound\"}, …]"`, read by each picker as `pickerValues: "@currencyOptions"`. It resolves from any screen or flow-step scope (same as `curTabId`), so adding an option is a one-line edit that can't reach one screen and miss another. Inline `pickerValues` arrays duplicated across two flows is how a currency ends up offered on New-tab but not Add-expense. (dave/whipround)

- **`selectInput.pickerValues` ids must be STRINGS — numeric ids validate clean but the runtime codec rejects the whole input.** `validate-org` passed `[{id: 1, label: …}]` with 0 findings and the org-pack harness never renders inputs, so the first sign was every radio on the live draft replaced by a red `Type mismatch … is not a Array<(string | ({ id: string, label: string } …` box. Use `"1"`…`"5"` (and a matching string `compute` default) and coerce in the script (`s1q1 * 1`) when you need arithmetic. Same class as the `autoAdvance` bullet above: a clean validator is necessary, not sufficient. (lab/energy-readiness, 2026-08-26)

- **To reset inputs, call `clearValues("name", …)` — it wipes each named node's value, descendants and repeating slots in one update, resolving names like a formula read (own scope outward, then any app-unique name), so a create-room flow on another screen can clear a game screen's section.** `setAppValue("<inputName>", "")` does NOT clear a sibling input (it writes an app-level key). A per-ROUND repeating section (`lineSlots`, `maxLength: round + 1`) gives a fresh box every round but REUSES the same pointer keys next game — Bandwagon's round-1 box showed the previous game's line until every new-game entry point (Play again, Join next, Host, Join) called `clearValues("lineSlots")`. Org packs run `clearValues` for real, so assert the value is gone. (2026-10-07)
- **A plain screen's inputs survive `navigate()` (only FLOWS under the target are reset), so an edit screen reached with `$args` shows the PREVIOUS record's typing.** Rallyround's role screen opened role B with A's name and shift settings, and its Save would have rebuilt B with them. Fix: wrap the form in a one-step flow with `hideNav` + `hideTopBar`, so every `navigate()` starts it fresh, however the last visit was left (clear-on-Back misses the phone's back gesture); verified live at 375px. `setValues({x: undefined})` does clear a sibling (`undefined` → `clearValue`; `""`/`null` STORE a value that hides the input's `compute` default). Until #1479 a clear followed by `navigate()` in the SAME script was silently undone — the unmounting input re-committed its stale text — so a pack test that stubs `setValues` cannot vouch for a clear; only a browser can (`orgs/dave/cockpit/e2e/`). The app also restores the last screen per ORG, not per `$variant`, so a variant-switching link should carry `?r=<screen>`. (dave/rallyround #2389)

- **A `numberInput` `variant: "slider"` shows no number at rest (MUI `valueLabelDisplay="auto"` — only while dragging), so a "how many" slider reads as a bare bar. Put the value in the label: `label: "@`Songs: ${songCount}`"`.** Labels are formula-capable and self-reference re-renders as the thumb moves. (dave/intro-quiz #2442)
- **`?preview=draft` does NOT stub a script's write hosts — `publishData`/`navigate` run for real there.** The `{id: "preview-stub"}` short-circuit in `scriptHosts.ts` fires only under `UiRoot mode="preview"`, which only `/demo` mounts (the old `deployMode: "dev"` gate is retired, #1511). So a signed-in draft run is a real end-to-end test of a save flow, and it writes real records. (#2442)
- **A multi-statement script must NOT end with `;` — `deleteData(…); deleteFile(Pic);` is a PARSE error (`Expected expression after ;`), while the same text without the final `;` runs.** `;` is a registered binary operator joining two expressions, so a trailing one has no right-hand side; the config corpus never carries one (`og validate-org` catches it as a formula-syntax finding), but a hand-written script in a test or a `data-script` attribute does. (#920)
